# probes/scoring: one prefill, N decisions on a language-model bundle

Not part of the SDK. It measures the primitive the typed-decisions API would use on a `.litertlm` bundle: prefill a rendered prompt once, save a checkpoint, score each candidate continuation, rewind between candidates. The published LiteRT-LM Kotlin API has no scoring or checkpoint call, so the probe uses the Kotlin sources and a JNI library built from the branch that adds them ([john-rocky/LiteRT-LM `kotlin-text-scoring`](https://github.com/john-rocky/LiteRT-LM/tree/kotlin-text-scoring): `Session.runTextScoring`, `saveCheckpoint`, `rewindToCheckpoint`, `rewindToStep`, `currentStep`, `SessionConfig.applyPromptTemplate`).

`sync.sh` copies the branch's sources and libraries in (they are never committed); the JNI the 2026-09-23 rows were taken with also carries `patches/litert-lm-3562-27c55edd.patch` (the pending fix of google-ai-edge/LiteRT-LM#3562 at 27c55edd, one hunk in `runtime/framework/resource_management/resource_manager.cc`, Apache-2.0), applied to the branch checkout before the bazel build in `sync.sh`; the test compares the phone's letter scores with a published oracle (the SemIf `authored144` rows rendered for Qwen3-0.6B, fp32 last-position logits over the letter slots; `src/androidTest/assets`) and times the shared arm against a fresh prefill per candidate:

```sh
probes/scoring/sync.sh ~/code/litert-lm-scoring-wt <dir with libLiteRt.so from litert-2.2.0.aar>
adb push qwen3_0_6b_mixed_int4.litertlm /data/local/tmp/hfmodels/
export ANDROID_SERIAL=<serial>
./gradlew :probes:scoring:connectedDebugAndroidTest -PscoringJniLibs=probes/scoring/jniLibs \
  -Pandroid.testInstrumentationRunnerArguments.model=/data/local/tmp/hfmodels/qwen3_0_6b_mixed_int4.litertlm \
  -Pandroid.testInstrumentationRunnerArguments.backend=gpu
adb logcat -d -s hfmodels-scoring | grep RESULT
adb shell run-as io.github.johnrocky.hfmodels.probe.scoring cat files/scoring/authored144_qwen3_0_6b_oracle-gpu.txt   # the same RESULT lines, kept when logcat rotates
```

Arguments: `model`, `backend` (gpu | cpu), `rows` (default all), `direct` (rows timed on the direct arm, default 12), `fixture` (asset name: `authored144_qwen3_0_6b_oracle.json`, or `authored144_minicpm5_2b_oracle.json` for `MiniCPM5-2B_int8.litertlm`, whose rows also carry the same bundle's own graph read on a Mac as `graph_probabilities`, and whose `strip_prefix` removes the literal `<s>` the bundle prepends itself as its start token). The `ok` of the `oracle` step is about the binding (the run completed and the score of a letter did not move after a rewind); agreement with the oracle is a measurement of the quantized bundle and is reported, not asserted. The per-row device probabilities land next to the RESULT lines as `<fixture>-<backend>.rows.jsonl`, in the form SemIf's `evaluate.py` reads.

`results/` holds the runs. On the Galaxy S26 (SM-S942Q, Android 16 BP4A.251205.006, 2026-09-23, the JNI built from the branch at 9073fcca with the #3562 fix applied, Qwen3-0.6B mixed_int4 at 154c5de0, the 144 authored144 rows, two runs per backend, warm medians): one decision on the shared arm (one prefill, three letters scored, a rewind between them) took 194 / 199 ms on the GPU and 1,040 / 987 ms on the CPU; the direct arm (a fresh prefill per letter) took 440 / 447 ms and 2,327 / 2,459 ms, so the shared arm cost 2.2 to 2.5 times less; the letter scores did not move after a rewind (drift 0.00000). On the GPU `runPrefill` returns in about 7 ms and the prefill's compute shows in the first scoring call (p90 about 150 ms). The phone went from thermal status 0 to 2 during the GPU runs; the numbers are one phone, one afternoon.

The same day, `MiniCPM5-2B_int8.litertlm` (litert-community/MiniCPM5-2B at f6dd64ef, sha256 61dafe88…) on the same phone with the `authored144_minicpm5_2b_oracle.json` fixture (the frozen SemIf ids rendered with the publisher's tokenizer; the literal `<s>` is stripped because the bundle declares it as its start token and the runtime prepends it, so the session held exactly the frozen 142-token prompt: `prefill_step_mismatch=0`): on the CPU every one of the 144 rows gave the same letter as the same bundle's own graph read on a Mac with ai-edge-litert 2.2.0, with probabilities equal to 2.7e-8, and SemIf's `evaluate.py` scores the rows at the Mac value (mean family balanced accuracy 0.6751; 140/144 letters agree with the fp32 oracle, as on the Mac); one decision took 4,596 ms (a 4.3 s prefill, then 109 ms per letter), the direct arm 13,133 ms. On the GPU one decision took 989 ms (prefill 449 ms, first letter about 370 ms, then 93 ms), the direct arm 1,288 ms; 23 of the 144 letters differ from the CPU and the Mac readout (mean |Δp| 0.12 against the graph rows; balanced accuracy 0.6882 on this run), which is the GPU arithmetic, not the binding (drift 0.00000). The phone did not reboot; its thermal status went 0 to 2 during each run.

`DecodeVsScoringDeviceTest` (same module, same arguments minus `direct`, plus `ids` = comma-separated row id prefixes) asks a narrower question about the GPU rows that disagree with the CPU rows: in one fresh session per row it takes the first streamed text of a greedy decode (`topK = 1`, cancelled after the first chunk), and in another the three letter scores, and writes both per row (`files/scoring/<fixture>-<backend>.decode.jsonl`, `ROW` and `RESULT` lines in logcat). If the greedy letter on the GPU also differs from the CPU's, the difference is in the GPU forward pass; if it agrees with the CPU while the scores differ, it is in the scoring path.

Run on 2026-09-24 (same phone, thermal status 2 throughout, the same patched JNI): on the GPU the greedy first letter and the scoring argmax agreed on 144/144 rows for `qwen3_0_6b_mixed_int4` and on 144/144 for `MiniCPM5-2B_int8`; on the CPU on 144/144 and on the 23 rows checked. Across backends the greedy letter differed on exactly the rows where the scores differed (23/144 for both bundles, the same 23 as on 2026-09-23), and on every one of them the GPU's greedy letter was the GPU's scoring letter, never the CPU's. So the GPU rows that disagree with the CPU come from the GPU forward pass itself (the next-token logits), not from the text-scoring path: a plain greedy decode on the GPU picks a different first token than the CPU on those prompts. Logs and per-row files: `results/2026-09-24-12*-decode-vs-scoring.*`.

What the runs showed on 2026-09-21: the binding works end to end; with the runtime as on `main` the score of the same letter changed after a rewind (up to 1.58 nats) and the top letter read far below the oracle, which is the double rewind reported in google-ai-edge/LiteRT-LM#3561; with the pending fix (#3562) applied the drift is 0.00000 and the top letter's log probability tracks the fp32 oracle within the quantized bundle's error. The runtime returns the log probability of the target (negative), not the negative log probability its header comment describes; the session reports one token more than the rendered prompt (a start token the runtime prepends).
