# Ids that load today

A model loads when its repo carries `hfmodels.json` (the publisher's declaration) or when the SDK's bundled catalog has an entry for it. The catalog pins each model to one commit and never re-hosts a file. The bundled catalog is public: <https://raw.githubusercontent.com/john-rocky/hfmodels-android/main/core/src/main/assets/hfmodels/catalog.json> (entries and their curated specs under `catalog/`).

Each cell is one run of the catalog gate (`tools/gate.sh`): a real download from the Hub with Range resume and a sha256 check, `prepare` on the named profile, one text turn (and one image turn for VLM profiles; for a thinking model the turn also has to put its reasoning in `channels` and none of the markers in the text). The records are in `verification/`, and those of the commits the catalog still pins are also inside the bundled catalog; the logs are `litertlm/results/2026-09-07-4C131JEKB15210-0.16.1-a3-gate.log` and `…/2026-09-08-…-a3-gate.log`. One phone, one day: not a promise for other devices. The Nemotron-3-Nano-4B row is not a gate run: on the Galaxy S26 a pushed copy of the file was imported (no download) and `ChatDeviceCheck` and `samples/chat` ran it; `Auto` takes `cpu` because that is the variant's default profile. The Hy-MT2-1.8B row is not a gate run either: on a Galaxy S26 a pushed copy of the file was imported (no download) and `samples/translate` loaded it with `Require(GPU)` and with `Require(CPU)`; `Auto` takes `cpu`, the variant's default profile. The NVIDIA-Nemotron-Labs-Dory1.0-4B row is not a gate run either: on a Galaxy S26 the phone downloaded both files from the Hub and `ChatDeviceCheck` ran them (`litertlm/results/2026-10-22-RFGL80R6A6H-litertlm0.16.1-dory-chat-check.log`); each variant has one profile and `Auto` never switches variants, so on a phone whose GPU cannot load `int4` the app asks for the CPU file itself: `ModelRef(id, variant = "int8")`. "Thinking" rows reason on every turn by default and get a 2,048-token output cap. A profile whose only record is a FAIL is skipped by `BackendPolicy.Auto` and stays available to `Require(GPU)` / `RequireProfile` for another phone; the two Qwen3.5 int8 bundles above 1 GB (2B, 4B) have specs but no entry yet, because their GPU run died the same way and their CPU weight cache (about 3.4 times the file) did not fit the free space of the gate phone.

On 2026-11-11 the same gate ran on a Pixel 11 Pro (16 GB, Android 17 CD1A.260905.001.B1) on LiteRT-LM 0.19.1, on the 65 `litert_lm` variants and profiles of the bundled catalog that the SDK loads on that runtime (all but the two of `Qwen3-4B-Instruct-2507`, at the end of this paragraph); the records are in `verification/2026-11-11-pixel11pro-CD1A.260905.001.B1.json`. 63 of the 65 answered. `gpu` ended the process for `Qwen3.5-0.8B` `int8` (Android's `MemoryLimiter:AnonSwap`) and for `Nemotron-3-Nano-4B` (recorded as FAIL, never auto-selected), and `cpu` answered for both. LiteRT-LM 0.19.1 hands a message's content to the chat template as a list of parts (0.16.1 handed a string), and an older file whose template expects a string fails at the first message or answers wrongly. The catalog now pins nine entries at a newer commit of their repo, whose files read that form: `Qwen2.5-1.5B-Instruct`, `LFM2.5-1.2B-Instruct`, `Qwen3-0.6B`, `LFM2.5-1.2B-Thinking`, `Qwen3-1.7B`, `Ministral-3-3B-Instruct-2512`, `Qwen3-4B`, `Qwen3.5-0.8B` and `Falcon-H1-1.5B-Instruct`. Their rows in the table were measured at the commits before. `Qwen3-4B-Instruct-2507` has no newer file on the Hub, so the catalog still declares it for LiteRT-LM below 0.18.0 only, and on 0.19.1 the SDK refuses to load it (`RUNTIME_VERSION_MISMATCH`).

Development shortcut: a copy of the file pushed into the app's external files directory (`adb push <file> /sdcard/Android/data/<applicationId>/files/`) is hashed and imported instead of downloaded; a file that does not match the descriptor's sha256 is ignored. `adb logcat -s hfmodels` prints one line per stage (`download`, `side-loaded`, `ready … profile=… prepare_ms=…`).

`ModelRef(id, revision = "<commit>", variant = "<id>")` pins more. Without a revision the first successful load binds the id to the commit it resolved, and later loads (also offline) use that binding until you call `unbind`.
